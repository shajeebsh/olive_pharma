# Setup and Installation

Step-by-step instructions for running OlivePharma locally and on Render.

## 1. Prerequisites

- Python 3.11+
- Git
- PostgreSQL 14+ **only if** you want to match production locally (SQLite is the default)
- A modern browser for testing the mobile layout with device mode

## 2. Installation

```bash
git clone https://github.com/shajeebsh/olive_pharma.git
cd olive_pharma

python3 -m venv .venv
source .venv/bin/activate

pip install -r requirements.txt
```

## 3. Environment Configuration

Copy the example environment file and adjust values:

```bash
cp .env.example .env
```

Key variables (`python-decouple` reads `.env` automatically):

| Variable | Local default | Render value | Purpose |
|----------|---------------|--------------|---------|
| `DJANGO_SETTINGS_MODULE` | `config.settings.dev` | `config.settings.prod` | Settings module |
| `DEBUG` | `True` | `False` | Debug mode |
| `SECRET_KEY` | dev-only value | generated by Render | Django secret |
| `DATABASE_URL` | `sqlite:///db.sqlite3` | from Render PostgreSQL | Database connection |
| `ALLOWED_HOSTS` | `*` (`dev.py`) | `.onrender.com` | Comma-separated hosts |
| `TIME_ZONE` | `UTC` | `UTC` | Display/storage time zone |
| `LOG_LEVEL` | `INFO` | `INFO` | Root log level |
| `WAGTAILADMIN_BASE_URL` | `http://localhost:8000` | `https://<service>.onrender.com` | Wagtail admin base URL |
| `PDF_BASE_URL` | `http://localhost:8000` | `https://<service>.onrender.com` | PDF export base URL |
| `PYTHON_VERSION` | not needed | `3.11.11` | Render Python runtime |
| `DJANGO_SUPERUSER_EMAIL` | blank | admin email | Admin username/email for provisioning |
| `DJANGO_SUPERUSER_PASSWORD` | blank | admin password | Admin password for provisioning |

`DJANGO_SUPERUSER_*` is only used by `ensure_superuser` (run by the deploy scripts). It is
optional locally; use `seed_demo` or `createsuperuser` for development accounts.

To use PostgreSQL locally, point `DATABASE_URL` at it:

```env
DATABASE_URL=postgres://user:password@localhost:5432/olive_pharma
```

## 4. Database Setup

```bash
python manage.py migrate

# Optional: demo users and sample field data
python manage.py seed_demo
```

`seed_demo` creates `admin`, `rep`, and `staff` users (password `password123`), a region,
hospital, doctor, pharmacy, products, a doctor visit, a chemist visit, a sale, a target,
and a check-in.

Create a real superuser when you are ready:

```bash
python manage.py createsuperuser
```

## 5. Running the Server

```bash
python manage.py runserver
```

- App: http://localhost:8000/
- Django admin: http://localhost:8000/django-admin/
- Wagtail CMS admin: http://localhost:8000/cms/
- Health check: http://localhost:8000/health/

## 6. Static and Media Files

```bash
# Rebuild production static output (run by build.sh and start.sh on Render)
python manage.py collectstatic --no-input
```

In development the app serves plain static files from `static/` without collectstatic.
Production uses `whitenoise.storage.CompressedStaticFilesStorage` with
`WHITENOISE_USE_FINDERS = True` (no manifest), so a missing `staticfiles/` directory or
manifest entry cannot break page rendering.

## 7. Settings Modules

| Module | Use |
|--------|-----|
| `config.settings.dev` | Local development (default via `manage.py`) |
| `config.settings.prod` | Render/production (`DEBUG=False`, secure cookies, HSTS) |

Production commands (equivalent to `start.sh`):

```bash
export DJANGO_SETTINGS_MODULE=config.settings.prod
python manage.py migrate --no-input
python manage.py ensure_superuser
python manage.py collectstatic --no-input
gunicorn config.wsgi:application --bind 0.0.0.0:8000 --workers 3 --timeout 120
```

## 8. Tests and Checks

```bash
python manage.py check
python manage.py test
```

## 9. Deploying to Render

The repository includes `render.yaml`, `build.sh`, and `start.sh`. Create a Blueprint from
the repo, or use the same values on a manually created Python web service.

Render deploys the branch configured on the service. This repository's default branch is
`main`, so merge `feature/postgres-build` into `main` (or point Render at the feature
branch) before expecting a fix on the live URL. If auto-deploy is disabled, use
**Manual Deploy → Deploy latest commit**.

| Render setting | Value |
|----------------|-------|
| Build Command | `./build.sh` |
| Start Command | `./start.sh` |
| Health Check Path | `/health/` |

### 9.1 Environment variables

Set these in the Render dashboard (or let the Blueprint create them). `SECRET_KEY` and
`DATABASE_URL` are generated/provided by Render.

| Variable | Required | Value / notes |
|----------|----------|---------------|
| `PYTHON_VERSION` | yes | `3.11.11` (fully qualified; do **not** use `pythonVersion` in `render.yaml`) |
| `DJANGO_SETTINGS_MODULE` | yes | `config.settings.prod` |
| `SECRET_KEY` | yes | generated by Render |
| `DEBUG` | yes | `False` |
| `ALLOWED_HOSTS` | yes | `.onrender.com` (add a custom domain if used) |
| `DATABASE_URL` | yes | injected from the Render PostgreSQL database |
| `LOG_LEVEL` | no | `INFO` |
| `TIME_ZONE` | no | `UTC` |
| `WAGTAILADMIN_BASE_URL` | no | `https://<service>.onrender.com` |
| `PDF_BASE_URL` | no | `https://<service>.onrender.com` |
| `DJANGO_SUPERUSER_EMAIL` | for admin | admin login; also used as the username |
| `DJANGO_SUPERUSER_PASSWORD` | for admin | admin password |

`DJANGO_SUPERUSER_*` is declared in `render.yaml` with `sync: false`, so Render prompts
for/keeps the values in the dashboard. Changing the password here and redeploying resets
the admin password to the environment value.

### 9.2 `build.sh`

`build.sh` is the Render **Build Command**. It runs at build time:

```bash
export DJANGO_SETTINGS_MODULE="${DJANGO_SETTINGS_MODULE:-config.settings.prod}"

pip install -r requirements.txt
python manage.py collectstatic --no-input
python manage.py migrate --no-input
python manage.py ensure_superuser
```

It installs dependencies, collects static files, applies migrations, and provisions the
admin. Because it touches the database, the build needs a reachable `DATABASE_URL`.

### 9.3 `start.sh`

`start.sh` is the Render **Start Command**. It runs on every instance boot:

```bash
export DJANGO_SETTINGS_MODULE="${DJANGO_SETTINGS_MODULE:-config.settings.prod}"

python manage.py migrate --no-input
python manage.py ensure_superuser
python manage.py collectstatic --no-input

# The work above already ran, so do not repeat it when the WSGI app loads.
export RUN_STARTUP_TASKS=0

exec gunicorn config.wsgi:application \
  --bind "0.0.0.0:${PORT:-8000}" \
  --workers 3 \
  --timeout 120
```

It re-applies migrations, re-provisions the admin, refreshes static files, then starts
Gunicorn on Render's `$PORT`. The repeated `migrate`/`collectstatic` steps make startup
self-healing if build output is missing.

### 9.4 Superuser provisioning

`ensure_superuser` creates the admin if missing, or updates the password and admin flags
if the account already exists (username = `DJANGO_SUPERUSER_EMAIL`). It runs from
`build.sh`, `start.sh`, the WSGI startup safety net, and a `post_migrate` receiver, so
any successful migration also provisions the admin. The deploy log should contain:

```
Superuser ready: admin@example.com
```

Log in with the email address in the **Username** field. To run it manually from the
Render Shell:

```bash
python manage.py ensure_superuser
```

If no superuser is created:

1. Confirm the deployed commit is the latest and the Render Build/Start commands are
   `./build.sh` and `./start.sh`.
2. Confirm both `DJANGO_SUPERUSER_EMAIL` and `DJANGO_SUPERUSER_PASSWORD` are set on the
   service.
3. Use **Manual Deploy → Clear build cache & deploy**, then search the log for
   `Superuser ready` or `Skipped: set both`.

### 9.5 WSGI startup safety net

Even if the Render Build/Start commands are still set to the old values, the WSGI entry
point (`config/wsgi.py`) calls `core.bootstrap.run_startup_tasks()` when production
settings are active or Render sets `RENDER=true`. That runs `migrate` and
`ensure_superuser` once per container before the first request, with a file lock so
Gunicorn workers do not repeat it. This fixes a missing session/auth table (a 500 on
login) and provisions the admin without editing the Render dashboard.

- The log shows `Startup tasks: applying migrations` and `Startup tasks: complete`.
- Set `RUN_STARTUP_TASKS=0` to disable this safety net; `start.sh` sets it after running
  the tasks itself.
- `RUN_STARTUP_TASKS=1` enables it outside Render (for example, a local production test).
- `/health/` now checks the database and the `django_migrations` table. It returns
  `200` with `"migrations": "ok"`, or `503` with `"migrations": "missing"` when the
  database has not been migrated.

### 9.6 Static files

Production uses WhiteNoise with `WHITENOISE_USE_FINDERS = True` and
`CompressedStaticFilesStorage` (no manifest), so static files are served even if the
`staticfiles/` output is missing at runtime.
